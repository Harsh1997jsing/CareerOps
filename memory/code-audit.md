# Full code audit — backend

A systematic sweep for issues *not* already documented in `known-gaps.md`
(tenant isolation, placeholder profile/evidence data, LibreOffice/ATS
PDF round-trip unverified, Jobo OAuth broken, no scheduled ingest sweep)
or `CONTRACT.md`. Three parallel read-only passes (dead code; correctness/
races/gaps) found the items below; every "Fixed" item was verified safe
and applied directly, with new or updated tests. Every "Recommended" item
is a real product/architecture/data-risk decision, not a bug, and was left
alone rather than guessed at. See `../CareerOps-frontend/CODE_AUDIT.md`
for the frontend's half of this same pass.

## Dead code (removed)

- `core/database.py`'s `get_database`/`get_db_engine` aliases — zero call sites anywhere.
- `core/exceptions.py`'s `DatabaseError`, `DatabaseConnectionError`, `NotFoundError` (+ its 4 subclasses `JobNotFoundError`/`ApplicationNotFoundError`/`UserNotFoundError`/`TenantNotFoundError`), `ForbiddenError` — never raised anywhere, and `app/services/auth.py` re-exported `TenantNotFoundError`/`UserNotFoundError` for "backward compatibility" despite never raising them either.
- `main.py`'s `not_found_exception_handler` (for the now-removed `NotFoundError`) — unreachable since day one; every real raise site of `ProtectedAdminError`/`InvalidCredentialsError`/`ConflictError` is already caught and converted to `HTTPException` locally in `routes/auth.py` before it could ever reach these handlers. Those three handlers themselves were *kept* as defense-in-depth for a future route that forgets to catch locally — just normalized to the same `{"detail": ...}` shape as everything else (see "JSON-response invariant" below).
- `app/schemas/domain.py`'s `Tenant`/`User` — shadow duplicates of the real ORM classes (`app.models.Tenant`/`User`) and the API `UserOut`/`TenantOut` schemas; nothing ever imported them.
- `services/applications.py`'s `approve_application()`/`reject_application()` — routes call `set_status()` directly since an earlier refactor.
- `llm/schemas.py`'s `ScreeningAnswer` — an unimplemented feature (screening-question auto-answering); no service ever referenced it.
- Unused test imports: `AsyncMock` in `tests/test_api_scrape.py`, `ConfigurationError`/`get_engine` in `tests/test_core.py`.
- `sources/jobspy_source.py` and `sources/targets.py` each had their own independent `_matches_experience()` — same shape, different haystack fields. Consolidated the actual matching logic into one `matches_experience(haystack, experience)` in `sources/common.py`; each source keeps its own `_experience_haystack()` for building its source-specific haystack text.

## Correctness fixes

- **JSON-response invariant (highest-impact fix)**: `llm/anthropic_client.py`'s `structured_call()` had no error handling, and none of its 8 call sites (`job_scorer`, `resume_generator`, `cover_letter`, `claim_validator`, `document_editor` ×2, `chat_search` ×2) caught anything either. Any Claude timeout/rate-limit/malformed-output — or an unrelated `KeyError`/`IntegrityError`/`RuntimeError` anywhere in a request — fell through to Starlette's default handler, which returns **plain text, not JSON**, for any exception not already registered (`Settings.debug` is defined but never actually passed to `FastAPI(...)`, confirmed by reading the installed Starlette source). Fixed: `structured_call()` now wraps `anthropic.APIError`/`pydantic.ValidationError` into a new `LLMServiceError` (`core/exceptions.py`), and `main.py` registers a handler for it (503 JSON) plus a catch-all `@app.exception_handler(Exception)` (500 JSON, logs server-side, never leaks the real exception message to the client) so **every** response from this API is now `{"detail": "..."}` JSON, matching CONTRACT.md, regardless of what actually failed. Every custom handler's body was also normalized to that same shape (previously `{"error": ..., "detail": ...}`). Tests: `tests/test_anthropic_client.py`, `tests/test_api_error_handling.py`.
  - Worth knowing if you add a bare `@app.exception_handler(Exception)`/500 handler again: Starlette's `Starlette.build_middleware_stack()` diverts a handler registered under the literal `Exception`/`500` key out of the normal per-type dispatch and into `ServerErrorMiddleware`, which **always re-raises after** calling it — the client still gets your handler's response in real deployment (uvicorn), but `TestClient`'s default `raise_server_exceptions=True` will surface the re-raise in tests. Test that path with a second `TestClient(app, raise_server_exceptions=False)`, as `test_api_error_handling.py` does.
- `services/document_review.py`'s `review_generated_document()`: `ats_validator.convert_docx_to_pdf()`'s `RuntimeError` (LibreOffice missing) wasn't caught between it and the route — `POST /jobs/{job_id}/documents` 500'd even though the `.docx`/`GeneratedDocument`/`Application` rows were already committed. Now caught; records `ats_check_passed = None` ("didn't run"), as CONTRACT.md already documents that value meaning, instead of failing the whole request. Tests: `tests/test_document_review.py`.
- `services/hard_filters.py`'s `check_hard_filters()` indexed `constraints[...]` directly — a `data/constraints.yaml` missing any key raised an uncaught `KeyError` through the foreground analyze path. Now uses `.get()` with fail-closed defaults (an incomplete constraints file blocks a job as unverifiable rather than crashing the request or silently admitting it). Tests: `tests/test_hard_filters.py`.
- `services/auth.py`'s `create_tenant()`/`create_user()` did check-then-insert with no `IntegrityError` handling around the commit, unlike `sources/common.py:insert_jobs()`'s established `begin_nested()`/`except IntegrityError` pattern — two concurrent signups with the same slug/email 500'd instead of the documented 409. Fixed with the same pattern. Tests: `tests/test_auth.py` (`test_create_tenant_concurrent_duplicate_slug_raises_from_commit`, `test_create_user_concurrent_duplicate_email_raises_from_commit`).
- `api/schemas.py`: `UserCreateRequest.email`/`TenantCreateRequest.name` had no format/length validation at all (unlike `password`/`slug` right next to them) — `{"email": ""}` created a permanent, unusable user row. Added a lightweight `local@domain.tld` shape check for email (**not** `pydantic.EmailStr`, which pulls in `email-validator` and rejects `.local` as a reserved-use TLD — this project's own default admin is `admin@careerops.local`, a deliberate local-first convention that a strict validator would break) and `min_length=1` for name. Also added `min_length=1` to `SuggestDocumentEditRequest.feedback` (an empty string previously spent a real Claude call for nothing). Tests: `tests/test_api_auth.py`, `tests/test_api_jobs.py`.
- `services/jobs.py`'s `list_jobs()` `q` param wasn't escaped before `.ilike(f"%{q}%")` — searching `q="50%"` was silently read as "contains 50" (the trailing `%` absorbed as a no-op wildcard) rather than requiring a literal `%`. Now escapes `%`/`_`/`\` and passes `escape="\\"` to `.ilike()`. Test: `tests/test_jobs.py::test_list_jobs_treats_a_literal_percent_in_q_as_literal_not_a_wildcard`.
- `api/routes/jobs.py`'s `list_documents` was the one `/jobs/{job_id}/...` route that never 404'd for a nonexistent job (`200 []` instead). Added the missing `_get_job_or_404()` call. Test: `tests/test_api_jobs.py::test_list_documents_returns_404_when_job_missing`.
- **Real resource leak**: `sources/mcp/client.py`'s `_make_client()` created a new `httpx.AsyncClient` per call and handed it to the MCP SDK as caller-provided — confirmed against the installed SDK source that a caller-provided client is never closed by the SDK, only the transport session is. Every `POST /explore/search` leaked 2 unclosed clients per configured MCP source, accumulating for the life of the process. Refactored into `_mcp_client()`, an `@asynccontextmanager` that owns the `httpx.AsyncClient` in its own `async with`, nested outside the `mcp.Client`'s — guarantees it's closed after every use, including on an exception. Tests: `tests/test_mcp_client.py`.
- `api/dependencies.py`'s `get_current_user()` built `UserContext.tenant_slug` from the JWT payload while re-reading every other field fresh from the DB in the same function — a tenant renamed after a token was issued would leave that one field stale for up to `JWT_ACCESS_TOKEN_EXPIRE_MINUTES`. Now re-reads the tenant's slug from the DB too. Test: `tests/test_dependencies.py`.

## Real gap, not dead code — company cooldown is now wired in

`check_cooldown_for_company()`/`check_company_cooldown()`/`get_company_applied_dates()` (`services/applications.py`, `services/hard_filters.py`) were fully implemented and unit-tested but `hard_filter_job()` never called them — the company-cooldown feature (block re-applying to a company within `constraints.yaml`'s `company_cooldown_days`) silently did nothing. `hard_filter_job()` is now `async` and takes a `session`, checking cooldown (when `company_cooldown_days` is set) right after the existing deterministic checks, before a job ever reaches the LLM scorer — same ordering CLAUDE.md's pipeline already requires for the other hard filters. Tests: `tests/test_jobs.py` (`test_hard_filter_job_fails_company_cooldown`, `test_hard_filter_job_passes_company_cooldown_when_no_history`).

## Race conditions (each needed a migration)

- **`Application` had no unique constraint on `job_id`.** Two concurrent `POST /jobs/{id}/documents` for the same job could both pass `create_application()`'s "does one exist" check before either committed, creating two `Application` rows for one job — every reader (`get_application_for_job()`, `get_job()`'s eager load) would then pick one nondeterministically. Migration `ae83e841285b` adds `uq_applications_job_id` (de-duplicating any existing rows first, keeping the oldest, so it applies cleanly against an existing database); `create_application()` now catches the resulting `IntegrityError` and re-queries for the winner's row instead of raising or duplicating. Test: `tests/test_applications.py::test_create_application_concurrent_race_returns_the_winners_row`.
- **`GeneratedDocument` had no unique constraint on `(job_id, type, version)`.** Same race shape, worse consequence: both concurrent requests compute the same next version from `_next_version()` and write to the *same on-disk filename* — the second write clobbers the first's file even though both rows would claim to describe it. Migration `048a9efe0048` adds `uq_generated_documents_job_type_version` (same de-dup-first approach); `persist_document()` now retries (up to 3 attempts) on `IntegrityError` — recomputing a fresh version and a correspondingly different filename each time, so a losing request never silently overwrites the winner's file. Tests: `tests/test_document_generator.py` (`test_generate_document_retries_on_a_version_collision`, `test_generate_document_raises_after_exhausting_version_retries`). Writing these tests caught a second, related bug in the fix itself: `session.rollback()` (called after the caught `IntegrityError`) expires *every* object in the session's identity map, not just the failed insert — a naive retry loop re-touching `job.id` on the next iteration crashed with `MissingGreenlet` (a sync lazy-refresh attempted outside the async context). Fixed by capturing `job_id = job.id` once, before the loop.
- **Auto-analyze (`explore.py`'s `_auto_analyze()` background task) vs. a foreground `/jobs/{id}/analyze` click** could both run against the same freshly-saved job, paying for two Claude calls for one job and leaving `Job.status` reflecting whichever commits last. `analyze_job()` now re-checks the job's *persisted* status immediately before the expensive scoring call, but only when the job was still at `DEFAULT_JOB_STATUS` ("DISCOVERED") when the call started — scoped specifically to that race, never blocking an intentional re-analyze of an already-scored job. Tests: `tests/test_jobs.py` (`test_analyze_job_skips_scoring_when_a_concurrent_analyze_already_won`, `test_analyze_job_reanalyze_of_an_already_scored_job_is_not_blocked_by_the_guard`) — the first required simulating the race with two genuinely independent `AsyncSession`s on one engine, since reusing one session for both the "concurrent" write and the guard check is a false pass (SQLAlchemy's ORM-enabled `UPDATE` auto-synchronizes any already-loaded object in the *same* session's identity map, which two real concurrent requests never do for each other).

## Refactored for consistency

- `services/document_review.py`'s `review_generated_document()` now accepts and threads through the caller's session (`document_generator.py`'s `persist_document()` passes its own live request-scoped one) instead of defaulting to `record_validation_result()`'s own separate session — matches every other service module, and keeps the whole persist-and-validate sequence on one connection/transaction.

## Flagged, not auto-fixed — needs a follow-up decision

- **`Evidence` ORM model + table (`app/models/evidence.py`) is fully unused.** The entire evidence pipeline (`job_scorer.py`, `cover_letter.py`, `claim_validator.py`, `resume_generator.py`, `document_editor.py`) reads `data/evidence.yaml` directly instead — this table has a real migration and a real schema but nothing ever queries, inserts, or reads through it. Looks like a leftover from before the YAML-based approach was adopted (see `memory/phase-2-document-generation.md`). **Recommendation**: either drop the model and write a migration to drop the table, or decide the YAML approach was always the intended design and just delete the vestigial model — either way this needs a real decision, since dropping a table (even an unused one) is a migration with data-loss risk on any database that happens to have rows in it, which isn't something to guess at silently.
- **`services/resume_generator.py`'s `generate_resume()` makes 5 sequential Claude calls** (one per resume section), where this codebase has its own established, working pattern for the identical shape — `services/chat_search.py`'s `summarize_results()` batches many-small-similar-LLM-calls into one. Batching resume generation would cut latency (5 round trips → 1) and failure surface (one call to retry instead of five independent ones) significantly. **Recommendation, not applied**: rewriting resume generation's actual prompt structure risks a real output-quality regression (fewer, more constrained tokens per section vs. one large combined prompt) with no existing test that would catch a quality drop — this needs a deliberate prompt-design pass and human review of sample output, not a mechanical refactor.
- **`services/auth.py`'s module-level `DEFAULT_ADMIN_EMAIL`/`DEFAULT_ADMIN_PASSWORD`/`DEFAULT_TENANT_NAME`/`DEFAULT_TENANT_SLUG` constants are evaluated once at import time** (`_settings = get_settings(); DEFAULT_ADMIN_EMAIL = _settings.default_admin_email`, etc.) — the exact pattern `core/config.py`'s own `get_settings()` docstring says this codebase deliberately avoids elsewhere ("required fields... would raise as a side effect of merely importing this module"). Investigated fixing this by converting the one live production usage (`authenticate_user()`'s `DEFAULT_TENANT_SLUG` fallback) to a call-time `get_settings()` lookup — but `DEFAULT_ADMIN_EMAIL`/`DEFAULT_ADMIN_PASSWORD`/`DEFAULT_TENANT_SLUG` are also imported as plain constants by `tests/test_api_auth.py` and `tests/test_auth.py` (30+ call sites) as an established test fixture convention. The actual risk this inconsistency represents (`get_settings.cache_clear()` being called mid-process) is confirmed never to happen anywhere in this codebase today — converting the constants to functions would mean an invasive test-suite rewrite for a purely theoretical benefit. Left as-is; noting the inconsistency here rather than silently leaving it undocumented.
